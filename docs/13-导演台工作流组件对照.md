### 0.6 尺寸三件套：比例 / 像素 / 宽高

> **口径（2026-09-21 定，人话版，先读这段）**：用户只选「比例 + 一采MP」，**前端按公式直接算出 32 倍数宽高，页面上当成固定值直接显示出来（只读，没有宽高手填框）** —— 这就是"**通过比例直接显示宽高，固定值**"。
>
> **页面侧（9 条完全一样，不分档）**：每个 `views/测试/*/index.js` 自己一份 `算画布()`（不共用），算出宽高 → 只读显示 → `watch` 回填 `表单.视频宽/视频高` 落库。
>
> **后端侧（按工作流分两档，不一样）**：
>
> | 档 | 工作流 | `填导演参数()` 传什么 | 谁算宽高 |
> | --- | --- | --- | --- |
> | **公式档** | **D2 / D6 / D7 / D8 / D9** | `兆像素=一采MP` + `比例` | **后端** `能力/导演台工具.py:由比例与像素算宽高()` 算 |
> | **自定义档** | **D1 / D3 / D4 / D5** | `宽=任务.视频宽` + `高=任务.视频高`，**不传** 兆像素 / 比例 | **不算**，直接用前端算好回填的那份 |
>
> 判据是工作流 JSON 的 `output.aspectRatio`：是官方 8 档之一 → 公式档；是 `自定义` → 自定义档（见下面「判定标准」逐条表）。
>
> **⚠️ 措辞纪律**：宽高在**前端就已经算出并显示给用户**了。后端那一份只是补一处实现（Django 直发 `/prompt`，API 模式没有浏览器，插件 JS 不执行，见源码追踪 ④），**不是口径**。提"后端换算"必须同时带上"前端已按同一公式算出并显示"。

每个工作流的 `timeline_data.output` 块里存了 7 个尺寸字段，**但 Python 只吃其中 3~4 个**：

| 字段            | 值（9 个工作流）                                        | Python 读不读                     |
| ------------- | ------------------------------------------------ | ------------------------------ |
| `mode`        | 全部 `fixed`                                       | ✅ 读（`fixed` / `long_edge` 二选一） |
| `aspectRatio` | `16:9 (宽屏)` / `9:16 (竖屏)` / `3:4 (竖版标准)` / `自定义` | ❌ **Director 一采完全不读**          |
| `megapixels`  | 全部 `0.4`                                         | ❌ **Director 一采完全不读**          |
| `multiple`    | `32`                                             | ❌ 不读，stride 写死 32              |
| `longEdge`    | `864`（D8 是 `736`）                                | ⚠️ 只在 `mode=long_edge` 时读      |
| **`width`**   | 864 / 480 / 576                                  | ✅ 读                            |
| **`height`**  | 480 / 864 / 736                                  | ✅ 读                            |

`resolve_output_dimensions`（`lib/image_prep.py:159`）：`mode=fixed` → `snap(width,32) / snap(height,32)`，`ref_max = max(w,h)`；`mode=long_edge` → 按长边等比缩放。**`stride` 从不从 `output.multiple` 传，默认 32**（`lib/image_prep.py:10 MINIMAX_CANVAS_STRIDE = 32`）。

#### 「像素 0.几」到底在哪

全库 `*.py` grep：`megapixel(s)` 只出现在 **`director/refine_pack.py`** 和 **`nodes/director_refine.py`** —— 都属于 **Refine（二采/放大）节点**，不属于 Director 一采。  
`/api/object_info/MiniMaxH3Director` 的输入里也**没有** `megapixels` / `aspect_ratio`，只有 `width` / `height` / `ref_max_size`（INT，step 32）。

所以：**Director 一采的画布就是像素宽高；`megapixels` 0.x 和 `aspectRatio` 是画布选择器的 UI 状态，存进 JSON 只是留痕，Python 不认。**

但工作流里那几个"整"的宽高**确实是从 0.4MP + 比例算出来的**。换算公式在插件 Python 里有一份（`director/refine_pack.py:231`，注释原文就是 "Director ResolutionSelector math"）：

```python
mp   = min(16.0, max(0.1, megapixels))     # 夹到 [0.1, 16]
mult = max(8, int(multiple or 32))         # 32
scale  = math.sqrt((mp * 1024 * 1024) / (w_ratio * h_ratio))
width  = int(round((w_ratio * scale) / mult) * mult)
height = int(round((h_ratio * scale) / mult) * mult)
# 最后 ensure_minimax_canvas() 再 snap 到 32 倍数
```

实测对账（9 个工作流一采全是 0.4MP）：

| 工作流         | aspectRatio  | MP  | 算出来     | JSON 里存的 | 反算实测 MP |
| ----------- | ------------ | --- | ------- | -------- | ------- |
| D1 D3 D4 D5 | `自定义`        | 0.4 | —（手填）   | 864×480  | 0.396   |
| D2          | `9:16 (竖屏)`  | 0.4 | 480×864 | 480×864  | 0.396   |
| D6 D7 D9    | `16:9 (宽屏)`  | 0.4 | 864×480 | 864×480  | 0.396   |
| D8          | `3:4 (竖版标准)` | 0.4 | 576×736 | 576×736  | 0.404   |

#### 判定标准（唯一口径，写死在这里，不准再换）

问"某个工作流的画布支不支持 / 是不是这套公式（比例 + MP → 32 倍数宽高）算出来的"，**只看工作流 JSON 里的事实**，分两步判定，不掺任何别的口径：

1. 打开 `backend/资源/工作流/<工作流>.json`，找 Director 节点（`class_type=MiniMaxH3Director`）的 `inputs.timeline_data`，取里面的 `output.aspectRatio` 与 `output.megapixels`。
2. 判定：
   - `aspectRatio` 是 8 档官方比例之一（`1:1 (方形)` / `2:3 (竖版照片)` / `3:2 (横版照片)` / `3:4 (竖版标准)` / `4:3 (标准)` / `9:16 (竖屏)` / `16:9 (宽屏)` / `21:9 (超宽)`）**且** `output.width/height` 等于该比例 + 该 MP 按公式算出的值 → **由这套公式产生** ✅
   - `aspectRatio = 自定义` → **不是**，宽高是手填值（可能恰好等于某一档的结果，但不是算出来的）
   - 节点上另有 `megapixels` / `aspect_ratio` 输入口（目前只有 D7 的 `MiniMaxH3DirectorRefine` 38）→ **运行时还会自己再算一次**，这是"原生吃 MP"的口

**⚠️ 这是三层不同的事，谁再拿其中一层当另一层的答案，就是错了**（2026-09-21 已经因为混层答错过一次，写死在这里）：

| 层 | 问法 | 判据 | 答案 |
| --- | --- | --- | --- |
| **第 1 层：工作流自带值** | 这个工作流 JSON 里存的宽高**是不是公式算出来的** | JSON 的 `aspectRatio` + `megapixels` + `width/height` 是否吻合 | **5 条：D2 / D6 / D7 / D8 / D9** ✅ |
| **第 2 层：运行时** | POST /prompt 之后**谁会自己再算一遍** | 节点有没有 `megapixels` / `aspect_ratio` 输入口 | **只有 D7 的 Refine 38**。Director 节点本身**没有** MP / 比例 口子（只有 `width`/`height`/`ref_max_size`，`nodes/director_common.py:61-63`）→ 其余 8 条运行时只认 `width/height` |
| **第 3 层：本后端传参** | 本 Django 给 Director **传的是什么** | `能力/*.py` 调 `填导演参数()` 的入参 | **跟第 1 层一致，分两档**：公式档 **D2/D6/D7/D8/D9** 传 `兆像素` + `比例`（后端算宽高）；自定义档 **D1/D3/D4/D5** 只传 `宽` + `高`（前端算好回填的那份），**不传** 兆像素 / 比例 |

**第 1 层和第 3 层是同一件事的两面**：工作流自带的宽高是不是公式算的（第 1 层），就决定后端该传「比例 + MP」让它自己算，还是直接传宽高（第 3 层）。**5 / 4 这条分界线只有一条，不许再出现"9 条一律"这种说法。**

**为什么自定义档不传比例 + MP**：那 4 条工作流的画布是作者手填的固定值（`aspectRatio=自定义`，插件走 `applyCustomResolution()`，不按 MP 算），它们本来就不认这套公式。后端传宽高 = 尊重工作流自带值；前端仍然按「比例 + MP」算出宽高显示并回填，所以用户在页面上改比例依然生效（宽高是前端算的）。两条路对默认档（16:9 + 0.4 → 864×480）结果相同。

### 0.8 原生官方提示词：t2va/fl2va 与 ref2va 是两套

#### 先回答三个问题

**Q1：多参考和首尾帧是不是还支持原生官方模型提示词？**  
**是，完全支持。** Director 最终把字符串原样交给 ComfyUI 官方节点（`nodes/conditioning.py:125-164`）：

```python
use_reference = (task_key in {"r2v","v2v","rv2v"}
                 or ref_images or ref_videos or ref_audios or ref_video_audios)
if use_reference: MiniMaxH3ReferenceToVideo.execute(clip=..., prompt=prompt, ...)  # ref2va
else:             MiniMaxH3ImageToVideo.execute(clip=..., prompt=prompt,
                                                first_frame=..., last_frame=...)   # t2va/fl2va
```

Director 的补标签 / fl2v 包裹都只是**在用户字符串前面加字**，官方 tokenizer 再按官方 presentation 拼。没有任何校验、截断或改写。

**Q2：我说的提示词规范是哪种模型的？**  
是 **ref2va = `MiniMaxH3ReferenceToVideo`**（多参考那条）的原生规范。  
该节点官方 description 原文：

> "<Picture i> / <Video k> / <Audio j> reference conditioning for MiniMax H3. **Use the same tags when prompting.**"

**首尾帧是另一套**（`MiniMaxH3ImageToVideo`，t2va/fl2va），规范不一样——见下表。

**Q3：什么有标准、什么必须原生？**

| 官方节点                        | 模型               | 走它的是                  | 原生规范                                                                                             |
| --------------------------- | ---------------- | --------------------- | ------------------------------------------------------------------------------------------------ |
| `MiniMaxH3ImageToVideo`     | **t2va / fl2va** | **D1 D3 D8**          | **无占位符标准**。fl2va 的首帧 = `<Picture 1>`、尾帧 = `<Picture 2>`（tokenizer 自动生成，用户可直接引用）；提示词本身是描述中间过程的纯文本 |
| `MiniMaxH3ReferenceToVideo` | **ref2va**       | **D2 D4 D5 D6 D7 D9** | **必须原生** `<Picture i>`(1~~9) / `<Video k>`(1~~3) / `<Audio j>`(1~3)，官方 description 明确要求          |

#### 官方 presentation（原文，`comfy/text_encoders/minimax.py` 文件头）

```
The H3 presentation is NOT chat-templated: token ids are raw prompt/label text
(no special tokens) with explicit vision blocks spliced in:

  t2va:   <prompt>
  fl2va:  "<Picture 1>: " <vision block> ["<Picture 2>: " <vision block>] <prompt>
  ref2va: per condition in request order (1-based ordinals per type):
            image -> "<Picture i>: " <vision block>
            audio -> "<Audio j>: "              (audio never enters Qwen)
            video -> "<Video k>: " then per 2-frame temporal block
                     "<T.T seconds>" <vision block(2 frames)>
          then <prompt>
```

要点：

- **用户提示词永远在最后**（所有视觉块之后）。所以 `reinforce_r2v_prompt` 把 `<Picture N>` 补在最前面是对的——它正好紧跟在视觉块后面。
- 不是 chat 模板，没有 special token；视觉块位置在 DiT 里带 token tag 0（video 模态），文本位置 tag 1。
- **audio 不进 Qwen**，只留一个 `<Audio j>: ` 标签。
- 参考视频的音轨 `<Audio j>` 排**在它自己的 `<Video k>` 前面**（`nodes_minimax_h3.py:283`）。

#### 两套规范逐项对照

|              | fl2va / t2va（ImageToVideo）                  | ref2va（ReferenceToVideo）                           |
| ------------ | ------------------------------------------- | -------------------------------------------------- |
| 走它的工作流       | D1 D3 D8                                    | D2 D4 D5 D6 D7 D9                                  |
| 原生标签         | 首帧 `<Picture 1>`、尾帧 `<Picture 2>`（**自动生成**） | `<Picture i>` / `<Video k>` / `<Audio j>`（**用户写**） |
| 官方是否强制       | ❌ 不强制，纯文本即可                                 | ✅ "Use the same tags when prompting"               |
| 编号基准         | 传图顺序 first=1 / last=2                       | 每类各自 1-based；总顺序固定为 **图像 → 视频（各带自己的音轨）→ 独立音频**     |
| Director 补标签 | 不补（t2v/fl2v 分支不动提示词，fl2v 只加中文锁定）            | 缺哪个补哪个（`reinforce_r2v_prompt`）                     |

#### 逐工作流：原生要求

| 工作流              | 官方节点                      | 原生提示词要求                                                                                          |
| ---------------- | ------------------------- | ------------------------------------------------------------------------------------------------ |
| D1 文生视频          | ImageToVideo (t2va)       | **无标准**，纯自然语言，随便写                                                                                |
| D3 首尾帧           | ImageToVideo (fl2va)      | 想指代帧就写 **`<Picture 1>` / `<Picture 2>`**（官方原生）；不写也行，帧靠 `minimax_keyframes` conditioning 锁定，与文字无关 |
| D8 分组图           | ImageToVideo (fl2va)      | 同上。有首/尾帧的组 Director 会加中文锁定；**组 4 无图 → 不加**                                                       |
| D2 / D6 / D7 多参考 | ReferenceToVideo (ref2va) | **必须用 `<Picture i>`** 指代参考图（i = refs 里的 index+1）。不写会被 Director 自动补在最前面                           |
| D4 视频生视频         | ReferenceToVideo (ref2va) | 源片固定绑成 **`<Video 1>`**（Bernini 风格）。不写 Director 会补                                                |
| D5 参考视频生视频       | ReferenceToVideo (ref2va) | `<Video 1>` = 源片，参考图 `<Picture i>`，参考音频 `<Audio j>`                                              |
| D9 分组多参考         | ReferenceToVideo (ref2va) | 组 `ref_images` → `<Picture i>`；组 `ref_videos` → `<Video k>`                                      |

#### 三套写法并存，互不兼容（重要）

| 出处                                                                     | 写法                                        | 给谁看                                                           |
| ---------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| **模型输入**（`comfy/text_encoders/minimax.py`）                             | `<Picture i>` / `<Video k>` / `<Audio j>` | **模型**，唯一真正生效的                                                |
| **Bernini 官方 PE 模板**（`lib/official_pe_templates.py`，bytedance/Bernini） | `image0` / `image1` / `image2`            | **LLM 改写提示词时用**，不是模型输入规范                                      |
| **Director fl2v 强化**（`director/fl2v_timeline.py:126-163`）              | `image0` / `image1` + 中文「完全保持首尾帧」         | 社区 cue word，`fl2v_timeline.py:130` 注释自称 "Community cue words" |

🔴 **分歧点**：官方 fl2va 的 presentation 是 `<Picture 1>: ` / `<Picture 2>: `，而 Director 的 fl2v 强化文本用的是 `image0` / `image1`（`_sanitize_fl2v_body` 还会把「参考图 image0」规范成 `image0`）——**两者对不上**。

## 附 C：硬规则

1. **帧数只认 17k+5**：`max(5, round(秒×帧率))` 再向上吸附。5s@24=124，1s@24=39。
2. **一采画布 = 宽×高像素，32 倍数**（`assert_minimax_canvas`，非 32 倍数直接报错）。`ref_max_size`/`longEdge` 只在 `output.mode=long_edge` 时生效；9 个工作流里 `output.mode` 都是 `fixed`。  
   **「像素 0.x（MP）」和「比例」是另一套**：它们存在 `output.megapixels` / `output.aspectRatio` 里，但 **Director 一采的 Python 完全不读**（全库 grep 只有 Refine 相关文件用到）。工作流里 864×480 / 480×864 / 576×736 就是 0.4MP + 比例套 §0.6 公式算出来的。  
   **页面的输入口径就是「比例 + MP」**（`03` 第 19 条 / `07` C11 / `10` B1）：用户选比例 + MP，**前端按 §0.6 公式直接算出 32 倍数宽高、在页面上显示成固定值**（只读，不许给宽高手填框），并回填 `视频宽/视频高` 落库。
   **后端按工作流分两档**（§0.6 总表，判据 = JSON 的 `output.aspectRatio`）：公式档 **D2/D6/D7/D8/D9** 传 `兆像素 + 比例`，由 `能力/导演台工具.py:由比例与像素算宽高()` 算出宽高；自定义档 **D1/D3/D4/D5** **直接传 `宽 + 高`**（前端算好的那份），**不传** 兆像素 / 比例。**不许写成"9 条一律传比例 + MP"。**
   **措辞纪律**：提"后端换算"必须同时带上"前端已按同一公式算出并显示"，否则会被理解成前端不显示宽高（2026-09-21 因此挨骂）。唯一原生吃 MP 的是 D7 的 Refine 节点 38（`megapixels` + `aspect_ratio`）。
3. **参数要写两处**：Director 的标量 widget（`width`/`height`/`ref_max_size`/`total_frames`/`frame_rate`/`cfg`/`seed`/`global_prompt`/`task_type`，这些**在** `/api/object_info` 的 INPUT_TYPES 里）**和** `timeline_data` 这个 STRING widget 里的同名字段。`timeline_data` 内部的 `segments` / `global` / `shots` / `output` / `video` 是 UI 塞进去的嵌套 JSON，Python 按 key 读，不写就取不到。
4. **D1/D2/D6/D7/D9 是 prompt_batch → 强制 segment**，只有 r2v+commonEnabled（D7）才合并 global。
5. **D4/D5 是 video+global**，只认 `global.*`，且**必须有源视频**。
6. **D3 走 shots[]**，segments 是空的。
7. **D8/D9 走连线**，timeline 完全不参与。
8. UNET 配对不是铁律：D9 是 r2v 却用 **fl2va**，D7 是 r2v 却用 **fl2va + turbo lora**。以工作流实际值为准。
9. 日志里带图的段会被前置模式指令（"完全保持首尾帧…"），只截前 ~60 字，看不到用户提示词。验顺序只能看纯提示词那段（D8 段 #4）。
10. **提示词在 ComfyUI 侧还会被加工一次**（§0.7）：t2v 不动；fl2v 强制加首尾帧硬锁定包裹；r2v/v2v/rv2v 缺 `<Picture N>` / `<Video 1>` / `<Audio J>` 时自动补在最前面。**后端不需要自己拼占位符，写了也行（写了就不会重复补）。**
11. **只有三种占位符**：`<Picture 1..9>` / `<Video 1..3>` / `<Audio 1..3>`。`subject_definitions:`、`<Subject N>`、`主体定义:` 是工作流作者自己写的正文，**插件不认**（它只做 `<Picture`/`<Video`/`<Audio` 的子串匹配）。`@` 引用只在节点 UI 有效，Python 不处理。
12. **没有 T5/system 前缀**，也没有自动提示词增强：`apply_task_system_prompt` 直接返回原文；`prompt_enhance_*`（Bernini 官方模板）只在节点 UI 手动触发，执行路径不调用。

14. 画布尺寸/时长**不要写进提示词**（D8 组 4 自带「15秒，16:9横版视频」，无效）。时长由 `duration_sec`、尺寸由 `output.width/height` 决定。
15. **两套模型两套规范（§0.8）**：`MiniMaxH3ImageToVideo`（t2va/fl2va）走 **D1 D3 D8**——无占位符标准，fl2va 的首/尾帧在 tokenizer 里是 `<Picture 1>` / `<Picture 2>`；`MiniMaxH3ReferenceToVideo`（ref2va）走 **D2 D4 D5 D6 D7 D9**——**必须**用 `<Picture i>` / `<Video k>` / `<Audio j>`，官方节点 description 原话 "Use the same tags when prompting"。
16. **原生提示词 100% 透传**：Director 只在字符串前面加字，不做校验/替换/截断，最后原样交给官方节点。所以按官方规范写一定能进模型。
17. **别写 `image0` / `image1`**：那是 Bernini PE 模板（给 LLM 改写用）和 Director fl2v 强化文本（社区 cue word）的写法，**和官方 tokenizer 的 `<Picture 1>`/`<Picture 2>` 对不上**。要指代首尾帧就写 `<Picture 1>` / `<Picture 2>`。
