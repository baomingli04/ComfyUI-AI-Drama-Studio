## 2. 选型点 P1：提示词规范

### 方案 A —— 原生官方规范（照 ComfyUI 源码）

**出处**：`ComfyUI/comfy/text_encoders/minimax.py` 文件头 + `comfy_extras/nodes_minimax_h3.py` 节点 description。

**写法**：

| 走的工作流 | 官方节点 | 提示词形态 |
|---|---|---|
| D1 文生视频 | ImageToVideo（t2va） | **裸文本**，无任何标签，随便写 |
| D3 首尾帧 / D8 分组图 | ImageToVideo（fl2va） | 想指代帧就写 `<Picture 1>`（首）/ `<Picture 2>`（尾）；不写也行 |
| D2 D4 D5 D6 D7 D9 | ReferenceToVideo（ref2va） | **必须** `<Picture i>`(1~9) / `<Video k>`(1~3) / `<Audio j>`(1~3) |

- ref2va 编号：**按请求内顺序、每类各自 1-based**（不是全混在一起编号）。
- 用户提示词永远在所有视觉块**之后**。
- 官方节点 description 原文要求："Use the same tags when prompting."

**优点**
- tokenizer 真认，标签 100% 生效。
- Director 的 `reinforce_r2v_prompt` 只在**缺标签时**补，不会重复叠加。
- 与 `03` 第 12 条天然兼容：页上写什么就发什么。

**缺点**
- 没有结构化段落，LLM 扩写时**容易漏参考项**（尤其参考多、还有音频时）。
- 长提示词组织性差，时序 / 声音 / 镜头容易写串。

---

### 方案 B —— 项目技能包规范（六段式，沿用旧项目）

**出处**：`backend/资源/技能/h3-prompt-writing/`（`SKILL.md` + `references/base-en.txt` 222 行 + `references/ref-en.txt` 336 行），后端 `能力/控制器/提示词扩写.py` 按它生成。

**写法**：ref2va 走六段

```
subject_definitions / summary / retention_analysis /
detailed_description / overall_soundscape / non_diegetic_music
```

标签四类：`<Subject N>`（可复用的可见内容）/ `<Picture N>`（参考图）/ `<Video N>`（参考视频）/ `<Audio N>`（音频）。
base 模式（T2VA / I2VA / FL2VA / L2VA）另有一套「指令句 + 三字段（`integrated_multimodal_description` / `overall_soundscape` / `non_diegetic_music`）」。

**优点**
- 结构强，LLM 好生成，参考项不易漏，`retention_analysis` 强制交代每个参考怎么用。
- 已经落地了：技能包、扩写控制器、前端 `共用/扩写行` 都在跑。

**缺点（已知风险，必须实测确认）**
- **`<Subject N>` 在官方 presentation 里没有出处**——官方只定义 `<Picture i>` / `<Audio j>` / `<Video k>`。模型大概率只把它当普通英文词，不产生 reference grounding。
- 六段的**字段名**（`subject_definitions` 等）会被原样喂进模型，属于非指令性文本污染。
- 与 Director 的 `reinforce_r2v_prompt` 可能叠加：技能包写了 `<Picture 1>` 时不补；若六段里只用 `<Subject 1>` 而没写 `<Picture i>`，Director 会**再补一遍 `<Picture i>`**，最终文本变成「六段式 + 尾部补标签」的混合体。
- 与 `03` 第 12 条不冲突（扩写结果会回填到页上、用户可见），但**页上看得见的文本变长很多**。

---

### P1 · A/B 对照

| 维度 | A 官方原生 | B 技能包六段式 |
|---|---|---|
| 标签是否被模型识别 | ✅ 官方定义，确定生效 | ⚠️ `<Picture/Video/Audio N>` 生效；`<Subject N>` **待实测** |
| 参考项漏写风险 | 高（无结构） | 低（六段强制交代） |
| 与 Director 补标签叠加 | 基本不叠加 | 可能叠加（缺 `<Picture i>` 时） |
| 落地成本 | 中（要改技能包 references + 扩写控制器提示词） | **0（已在跑）** |
| LLM 生成稳定性 | 中 | 高 |
| 文本污染 | 无 | 有（字段名入模） |
| 适用面 | t2va/fl2va/ref2va 全覆盖 | 主要 ref2va；base 模式另有一套 |

**判定后若要选 A，最小改法**：把 `ref-en.txt` 的 `<Subject N>` 段落**降级为纯文本描述**（去掉尖括号标签，或标注"仅供 LLM 组织思路，不得输出"），六段结构可保留；`base-en.txt` 的 I2VA/FL2VA 指令句是普通英文描述句，与官方 `<Picture 1>/<Picture 2>` 不冲突，可保留。

## 3. 选型点 P2：尺寸口径

### 方案 A —— 像素直传（导演台现状）

- 页面只给 **视频宽 / 视频高**（必须是 **32 的倍数**）。
- 后端 `能力/*.py` 直接写 Director 标量 `width`/`height` + `timeline_data.output.width/height`。
- 适用于 **D1–D9 全部一采**（`/api/object_info/MiniMaxH3Director` 只有 `width`/`height`/`ref_max_size`，**没有** `megapixels`/`aspect_ratio`）。
- **缺点**：用户得自己算 32 倍数，不直观；换比例要手算。

### 方案 B —— 比例 + MP，前端直接显示宽高（旧项目 / Refine 口径）

- 页面给 **比例**（16:9 / 9:16 / …）+ **一采MP**（0.x，如 0.4）+ **二采MP**。
- 后端套 `director/refine_pack.py:231` 的公式换算：

```python
mp    = min(16.0, max(0.1, megapixels))
mult  = 32
scale = math.sqrt((mp * 1024 * 1024) / (w_ratio * h_ratio))
width  = int(round((w_ratio * scale) / mult) * mult)
height = int(round((h_ratio * scale) / mult) * mult)
```

  再写 `output.width/height` + Director 标量。
- **缺点**：一采这步换算**必须后端自己实现**（ComfyUI 一采不会替你算），且要与前端显示值一致；多一层出错面。
- **只有 D7 的 Refine 节点（`MiniMaxH3DirectorRefine`）是原生吃比例 + MP 的**，其余一采都不是。

### P2 · A/B 对照

| 维度 | A 像素直传 | B 比例 + MP 换算 |
|---|---|---|
| 一采是否需要后端再算一次 | 不需要 | **需要**（前端已按公式算出并显示，后端因 API 模式无浏览器要再算一次写进 Director） |
| 页面直观性 | 差（手算 32 倍数） | 好（下拉选比例 + 填 0.4） |
| D7 二采 | 不适用（Refine 吃 MP） | ✅ 原生支持 |
| 落地成本 | **0（已跑通 9 个）** | 中（后端加换算 + 前端改表单） |
| 与 `10` B1/B2 旧口径 | 相反 | 一致 |

> **已统一（2026-09-21）**：一采也走 B。9 个 `能力/*.py` 现在传 `比例 + 一采MP`，由 `导演台工具.由比例与像素算宽高()` 套 `refine_pack.py:231` 公式换算成 32 倍数像素后再写 Director；`任务.视频宽/视频高` 仍由前端 watcher 回填（DB 列有值），但**不再是用户输入源**。D7 二采 Refine 节点 38 依旧原生吃 MP + 比例，两条路径公式同源。

### ✅ P2 已定（2026-09-21）：走方案 B

用户拍板：**页面就给「比例 + 一采MP」，宽高是按这两者算出来的固定值、只读显示**，不许让用户手填宽高——`docs/03` 第 19 条、`docs/07` C11、`docs/10` B1 从来都是这个口径。

落地：

| 层 | 改动 |
|---|---|
| `能力/导演台工具.py` | 新增 `由比例与像素算宽高(比例, 兆像素)`（套 `refine_pack.py:231` 公式，MP 夹 [0.1,16]，snap 32）；`填导演参数` 新增 `兆像素` / `比例` 入参，**给了就以它们为准**，算不出来才回落 `宽/高` |
| 9 个 `能力/*.py` | 统一加传 `兆像素=任务.一采MP`、`比例=任务.比例` |
| 9 个 `views/测试/*/index.js`（各页面自己一份，不共用） | `比例选项` + `算画布()` + `画布宽高` computed + watcher 把算出的像素同步回 `表单.视频宽/视频高`（保证 DB 列仍有值） |
| 9 个页面 | 宽/高 两个数字输入框 → 「比例」下拉 + 「一采MP」输入 + **只读画布显示** |
| D7 | 一采和二采**共用 `表单.比例`**（二采选「跟随导演台」时一采回落手填兜底值），一采 MP 与二采 MP 各一列 |

换算自检（与工作流自带值完全对得上）：`16:9 + 0.4MP → 864×480`、`9:16 + 0.4MP → 480×864`、`3:4 + 0.4MP → 576×736`、`16:9 + 2MP → 1920×1088`（= D7 Refine 节点里的值）。

## 4. 澄清 C3：加工方不是本后端（这条不改 `03`）

`03-AI使用规范.md` 第 12 条「**禁止后端拼接提示词**。发给 Comfy / LLM 的文本必须等于前端提交、页上能看见的那一份」——**继续有效，不修改**。

边界说清楚：

| 环节 | 谁在做 | 受第 12 条约束 |
|---|---|---|
| Django 后端（`能力/*.py`） | 只 `rstrip()`，不拼接 | ✅ 受约束 |
| ComfyUI 插件 Director（`executor_core.py:774-814`） | 按 `task_key` 分发：fl2v 加中文锁定包裹、r2v 补 `<Picture i>` 标签 + drop 不可用音频标签、v2v/rv2v 各自 reinforce | ❌ **不受约束**（不是本后端，也不由本项目控制） |
| ComfyUI 官方 tokenizer | 按官方 presentation 拼 `<Picture i>: ` + 视觉块 + prompt | ❌ 不受约束 |

**第 12 条约束的是「本后端代码」，不是「整条链路的最终文本」。** 链路下游（ComfyUI 侧）的加工无法禁止，也不该禁止——那是官方节点行为。

## 5. 选型判据（怎么验出哪套好用）

**必须最小化测试**（`09` 纪律）：256×160（都是 32 倍数）、**1 秒**、帧率沿用工作流默认的 24 → 39 帧；不要上大画布长视频。

**P1 判据（提示词规范）** —— 用 **D2 多参考**（ref2va，最能暴露标签问题）同一 seed 跑两版：

| 观察点 | A 胜的迹象 | B 胜的迹象 |
|---|---|---|
| 参考人物/物体还原度 | A 明显更像参考图 | B 更像，或两者持平 |
| ComfyUI 日志里 `reinforce_r2v_prompt` 是否又补了标签 | 没补（说明标签已被识别） | 补了（说明 B 的 `<Subject N>` 没顶用） |
| 出片时长 / 帧数 | 两者应一致（39 帧），不一致说明提示词影响了时序 | — |
| 单段耗时 | 短者优（长文本会增加 Qwen 编码开销） | — |

**P2 判据（尺寸口径）** —— 只在「一采页面要不要给 MP 入口」上做一次判断：
- 若按公式算出的宽高与手填 32 倍数**逐档一致**（0.4MP + 16:9 → 864×480 这类对照已在 `13` §0.6 对账通过）→ 两套等价，**维持 A**，不必新增换算通道。
- 若用户明确要 MP 下拉 → 走 B，后端加换算，并把对账表补进回归测试。
